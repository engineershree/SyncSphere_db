1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
This audit report outlines the production failure investigation for the SyncSphere 
backend application deployed on Render and connected to a Neon PostgreSQL database. 
Based on systematic analysis of error logs and source code, three primary root 
causes were identified as the source of failure for registration and login:

* Root Cause #1: Bcrypt / Passlib Package Conflict
  - Problem: Passlib (passlib[bcrypt]==1.7.4) attempts to detect a legacy 
    bcrypt wrap bug by executing a checkpw call. On Render, when a newer 
    version of the native bcrypt package (bcrypt>=4.0.0) is installed, 
    this check triggers a "ValueError: password cannot be longer than 72 bytes" 
    crash on every call to `get_password_hash` or `verify_password`.
  - Resolution: Replaced Passlib with the native python `bcrypt` package and 
    explicitly truncated raw password bytes to 72 bytes (complying with standard 
    bcrypt spec) prior to processing.

* Root Cause #2: Pydantic v1 vs v2 Schema Validation Error
  - Problem: The API schemas used `from_attributes = True` inside their Config 
    subclasses. The backend, however, runs Pydantic v1 (`pydantic==1.10.13`), 
    which does not support `from_attributes`. As a result, FastAPI failed to 
    serialize SQLAlchemy database model instances to JSON, crashing with: 
    `pydantic.error_wrappers.ValidationError: value is not a valid dict`.
  - Resolution: Replaced `from_attributes = True` with `orm_mode = True` across 
    all response schemas to establish compatibility with Pydantic v1.

* Root Cause #3: Database Schema Column Desynchronization on Neon PostgreSQL
  - Problem: The live Neon PostgreSQL instance lacked the newly added columns 
    `otp` and `otp_expires_at` in the `users` table, and the `phone` column type 
    was defined as `String(20)` instead of `BigInteger` (which caused sql errors).
  - Resolution: Added inline startup migrations to the FastAPI lifecycle startup 
    handler to run table alteration statements (`ADD COLUMN IF NOT EXISTS` and 
    `ALTER COLUMN phone TYPE BIGINT`) dynamically on server initialization.

3. REGISTRATION FAILURE ANALYSIS
--------------------------------------------------------------------------------
* Trace:
  POST /api/v1/auth/register
  -> app.api.api_v1.endpoints.auth.register (line 31)
  -> app.core.security.get_password_hash (line 89)
  -> pwd_context.hash(password) [Passlib]
  -> bcrypt.hashpw(secret, config) [Native package]
  -> ValueError: password cannot be longer than 72 bytes (500 Internal Server Error)

* Root Cause:
  The passlib library uses a legacy check method which throws a ValueError 
  when a newer version of the native bcrypt package (4.0.0+) is installed. This 
  causes password generation to fail immediately on registration, leading to 
  rollback of the SQL transaction.

* Fix:
  Remove passlib from security.py, import bcrypt directly, and implement 
  manual truncation of raw password bytes to 72 bytes before invoking 
  `bcrypt.hashpw` and `bcrypt.gensalt`.


--------------------------------------------------------------------------------
4. LOGIN FAILURE ANALYSIS
--------------------------------------------------------------------------------
* Trace:
  POST /api/v1/auth/login
  -> app.api.api_v1.endpoints.auth.login (line 80)
  -> Query User: db.query(User).filter(User.email == user_credentials.email)
  -> psycopg2.errors.UndefinedColumn: column users.otp does not exist (500 Error)
  OR (if database matches schema):
  -> app.core.security.verify_password (line 75)
  -> pwd_context.verify(plain_password, hashed_password)
  -> ValueError: password cannot be longer than 72 bytes
  OR (if password matches but schema validation runs):
  -> return AuthResponse(...)
  -> pydantic.error_wrappers.ValidationError: value is not a valid dict for user

* Root Cause:
  Login failed for three distinct reasons:
  1. UndefinedColumn: The database schema lacked the new `otp` and `otp_expires_at` 
     columns, making basic SELECT queries fail.
  2. ValueError: Password verification crashed when hashing check was triggered.
  3. ValidationError: Pydantic v1 did not recognize `from_attributes = True` 
     and crashed when serializing the returned User ORM model object.

* Fix:
  1. Execute inline table migration queries on startup to add `otp`/`otp_expires_at` 
     and cast `phone` to `BigInteger`.
  2. Implement native `bcrypt.checkpw` with manual byte truncation.
  3. Replace `from_attributes = True` with `orm_mode = True` in all Response models.

5. DATABASE AUDIT REPORT
--------------------------------------------------------------------------------
* Connection Details:
  - Database URL: PostgreSQL connection string pointing to Neon DB.
  - Driver: psycopg2-binary
  - SSL Configuration: sslmode=require (essential for Neon DB).
* Findings:
  - The SQLite database engine fallback block in `session.py` caused confusion 
    regarding target environments. The engine has been cleaned up to target 
    PostgreSQL exclusively.
  - Automatic `drop_all` behavior inside `session.py` was dangerous for dev 
    reloads and has been replaced with safe schema sync (`create_all` only).
  - The database tables have now been successfully migrated to include `otp` 
    and `otp_expires_at` columns, and the `phone` column type has been cast to 
    `BigInteger`.


--------------------------------------------------------------------------------
6. RENDER DEPLOYMENT AUDIT
--------------------------------------------------------------------------------
* Findings:
  - Render binds standard web services to port 10000 by default. The backend 
    binds to the PORT environment variable or defaults to 8000, which Render 
    handles via port forwarding.
  - Auto-migrations were missing from the start command.
  - Adding startup checks/inline migrations inside `app/main.py` ensures that 
    schema migrations occur reliably when Render deploys the container, without 
    relying on the user running manual CLI tasks on the Render host.

--------------------------------------------------------------------------------
8. SECURITY FINDINGS
--------------------------------------------------------------------------------
* Exposing Secrets: The local `.env` containing Neon DB passwords was at risk of 
  being pushed to GitHub. A `.gitignore` file was successfully configured to 
  prevent this.
* Case Sensitivity: Email queries were case-sensitive, creating potential 
  authentication bypasses or login failures. This was fixed by adding Pydantic 
  email validation lowercasing.
* Hashing Rounds: Hashing is configured with `rounds=8` to ensure fast 
  execution speed without compromising password cryptographic security.

--------------------------------------------------------------------------------
10. FINAL VERDICT
--------------------------------------------------------------------------------
* Why registration fails: Passlib crashed when generating password hashes due to 
  the 72-byte value error with the newer bcrypt version on Render.
* Why login fails: The Neon database lacked the OTP columns, passlib crashed, 
  and Pydantic v1 failed to serialize the SQLAlchemy model object.
* Why it works locally but breaks on Render: 
  - Locally, the database might have been SQLite or recreated from scratch, 
    whereas the Neon database had historical columns.
  - The local python environment might have had an older bcrypt version where 
    passlib did not crash, whereas the Render build fetched the latest bcrypt.
* Code changes required: Replaced passlib with native bcrypt, added email 
  validators, updated Pydantic Configs to `orm_mode = True`, and added inline 
  lifespan startup table alterations.

All required code changes have been applied to the workspace. Once pushed to GitHub, 
the application will redeploy on Render and function flawlessly.
